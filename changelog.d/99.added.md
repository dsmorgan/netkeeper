`netkeeper.linkedin.classify.classify(response, url, body)` (spec 9.7): maps a LinkedIn response to one of six outcomes (`Ok`, `Throttled`, `Checkpoint`, `LoggedOut`, `NotFound`, `RouteChanged`), pure and behind the extractor boundary (ADR 0005, spec 9.10). A checkpoint or login-wall signal in the url, or in the body when the body is not recognizable JSON, outranks the HTTP status, because the status alone lies in both directions: a `429` can be a checkpoint page in disguise, and a `200` can be a login wall LinkedIn served at the original request url instead of redirecting to it. The body scan is restricted to a non-JSON body specifically so a contact's own data — a personal website ending in `/login`, a tracking url carrying `/checkpoint/` — is never misread as a session signal. Any status spec 9.7's table does not name (403, 5xx) folds into `RouteChanged` as a documented conservative default. `is_retryable(outcome)` is the one place "never retry a checkpoint" is decided, for a future job loop to consult. Spec 9.7's `LoggedOut` row is amended to name the body alongside the redirect, matching this module's one interpretive call beyond the table's literal wording. On the core side of the boundary, `netkeeper.services.linkedin_session.flag_session()` turns a `Checkpoint` or `LoggedOut` outcome into a `settings_kv` record (`linkedin.session_flag`, path only — a checkpoint or login-wall url's query-string token is dropped) a future banner can read back with `session_flag()` and remove with `clear_session_flag()`; it refuses every other outcome rather than writing a flag spec 9.7 never asked for.
