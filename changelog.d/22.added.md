The import wizard at `/imports` (spec 10.5): choose a CSV, map its columns from a detected preset or by hand, preview the first twenty rows resolved against your contacts, decide each candidate, and commit. The preview names the fields provenance will refuse — a value your own edit outranks is the one thing you cannot find out after committing — and the cells the importer dropped on rows that still land, such as a LinkedIn URN that is not a `urn:li:…`. Commit stays out of reach while a candidate has no decision, rather than answering 409 after the click; undecided candidates can be skipped deliberately instead. `/imports/runs` lists every run with its counts and status, and a run's own page rolls it back after spelling out what that deletes, what it puts back, and that a merge since the import refuses the rollback whole. A draft that was read but never committed can be finished from there without choosing the file again.

The wizard reads the file's bytes and works out its encoding rather than assuming UTF-8 (issue #79). A byte-order mark settles it, UTF-16 without one is recognised by its zero bytes, valid UTF-8 is UTF-8, and anything else is read as Windows-1252 — the encoding Excel and older Windows CRMs write. `POST /imports/inspect` no longer refuses a file whose headers no preset recognizes. It writes nothing and exists to show a file's columns, so it returns them with an empty mapping and leaves the requirement that an import map *something* to `POST /imports`, which is the call that writes. Before this, any CSV from anything but LinkedIn answered 422 on upload and the screen that could have mapped it by hand was unreachable.

A run records the preset it was read with only when nothing edited what that preset produced. Editing one column used to leave the run filed under `linkedin-archive` with a mapping that was no longer the linkedin-archive mapping, which every screen reading `preset` then repeated.
