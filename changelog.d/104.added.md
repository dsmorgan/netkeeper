A DOM fallback for the two paths spec 9.3 names as mattering most: `netkeeper.linkedin.dom`'s `DomConnectionsSource` enumerates the connections list by scrolling like a person (`linkedin/pacing.py`'s `scroll_like_a_person`, replayed through `BrowserRun.scroll`) and reading rendered cards through read-only `page.evaluate` queries, and `DomContactInfoSource` reads the contact-info overlay by navigating straight to its own url (the same one a "Contact info" link points at) rather than simulating a click. Both implement the same protocols the in-page Voyager sources already do (`ConnectionsSource`; the new `netkeeper.linkedin.contact_info.ContactInfoSource`), and `FallbackConnectionsSource`/`FallbackContactInfoSource` (in `connections.py` and `contact_info.py`, pure, no browser) switch a run from the API source to the DOM one automatically, once, the first time the API answers `RouteChanged` -- never back, and never spending an extra budgeted unit of work on the page that needed both. A DOM-sourced connection carries no URN (LinkedIn's internal id is not in the rendered page) and every DOM page reports its total as unknown, so `SyncResult.complete` can only be true when an earlier Voyager page already proved the total by URN; a full sync that falls back to DOM can enumerate the whole visible list and still, correctly, never age anyone on the strength of what DOM alone saw. `crm.apply._mark_seen` now clears a miss count or a disconnect by public id as well as by URN, so a contact's reappearance is still recognized when the page that saw them came from DOM. Contact-info's API implementation (`ApiContactInfoSource`) is ready for enrichment (P2-07) to adopt in place of its direct Voyager call; that wiring is a follow-up. Selectors are authored from LinkedIn's URL routing and ordinary HTML conventions (`mailto:`, `tel:`), not captured from a live session (see `voyager.py`'s "capture date" note and #149), and degrade to `RouteChanged` rather than silently misreading a page -- including a login wall or checkpoint, which is classified from the tab's own url rather than parsed as an empty list. `tests/smoke/test_dom_smoke.py` proves the scroll mechanism and the overlay reader against a hand-built local HTML replica whose own script gates new cards on real `scroll` events, driven by a real Chrome.
