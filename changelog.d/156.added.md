`netkeeper simulate --days N --throttles K --seed S`, the last of CP3's three commands (#107).

Replays `N` simulated days of the schedule against a scratch SQLite database this command creates and deletes itself — seeded cold from `[linkedin]` config (budgets, pacing, heat, active hours, timezone), never from a real account's `settings_kv` counters, and never against `netkeeper serve`'s own database. The run always starts on a fixed reference Monday so a given `--seed` reproduces byte-identical output regardless of when the command is actually run, and a fortnight (or longer) always crosses a weekend for the damping to show.

For each simulated day it reports the warm-up-ramped, weekend-damped, heat-shrunk profile-visit allowance against what was actually spent; the heat score and whether it tripped the skip gate; how many of the requested throttles landed that day; and every scheduled job kind's fires (fired, heat-skipped, catch-up). `--throttles K` marks `K` `Throttled` outcomes at points drawn from `--seed`, each fed through the real `netkeeper.services.heat.raise_heat` — heat rising, the cooldown multiplier stretching, the derived per-day budget shrinking, and (with enough of them close together) the heat-skip gate suppressing further browser jobs are all the genuine consequences a live run would see, not a picture of them. Two throttled units in a row abort that fire's spend loop, per spec 9.7's classify table.

The injected `JobKind.ENRICH` handler is the first real caller anywhere in the package of `budgets.consume`, `raise_heat`, `warmup_budget`, and `apply_weekend_multiplier` — `tests/test_posture.py`'s AST scan for `UNENFORCED_TODAY` now excludes `netkeeper/services/simulate_run.py` by name, with a comment explaining why (a simulation spending a scratch account's budget is not production enforcement), rather than letting the gap list shrink over a gap that has not actually closed.

Nothing here imports a browser, contacts linkedin.com, or arms a real scheduler.
