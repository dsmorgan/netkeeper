Two of CP3's three commands: `netkeeper posture` and `netkeeper rehearse`.

`netkeeper.services.posture` answers "is this safe to run?" in one place, and is built around one property: **a protection that is off, bypassed, or configured past spec 9.6's hard maximum always produces a warning.** It covers attach-only browsing and the debug port it attaches to (ADR 0002), whether a LinkedIn session is actually present, the session flag a `Checkpoint` or `LoggedOut` classification raises (spec 9.7), the active window and where now falls in it, whether budget days and active hours roll over at the same local midnight, the weekend multiplier, the warm-up ramp, LinkedIn auto-send (ADR 0004), every per-day and per-week budget counter against its limit *and* against spec 9.6's hard max, the heat score with when it was last raised and when runs resume, the scheduler's heat skip gate, and whether a schedule is established at all. It reports today's profile-visit budget as the chain that produced it — warm-up ramp, then weekend damping, then the heat cooldown — and states the gaps it cannot see rather than omitting them. `Protection` refuses to exist with a status other than `on` and no warning to go with it, so an "all clear" that hides a disabled protection is structurally impossible; the tests turn each protection off in turn and assert the report warns about that one and only that one. Read-only: it takes no write lock and changes nothing.

`netkeeper rehearse` drives the genuine attach path through the genuine pacing plan — the same scroll deltas, dwell, lognormal waits and bursts a real enrichment run uses — against a profile-shaped replica served on this machine's loopback, and prints every request the tab made: method, status, kind, timing, path, grouped by visit. **It cannot reach LinkedIn:** a linkedin.com host is refused by name, any other off-machine host is refused as not loopback, both before a browser connection exists, and a rehearsal whose page nevertheless reached one raises rather than reporting. The command starts and shuts down the loopback replica itself, so the demo is one command; `--seed` repeats a rehearsal line for line and `--scale` divides the waits, which the log then marks so a scaled rehearsal can never be mistaken for a real one. Nothing launches a browser, nothing opens a database, and requests are observed through a page listener rather than intercepted, so the log records what the browser genuinely sent.
