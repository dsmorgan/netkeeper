Two of CP3's three commands: `netkeeper posture` and `netkeeper rehearse`.

`netkeeper.services.posture` answers "is this safe to run?" in one place, and is built around one property: **a protection that is off, bypassed, or configured past spec 9.6's hard maximum always produces a warning.** It covers attach-only browsing and the debug port it attaches to (ADR 0002), whether a LinkedIn session is actually present, the session flag a `Checkpoint` or `LoggedOut` classification raises (spec 9.7), the active window and where now falls in it, whether budget days and active hours roll over at the same local midnight, the weekend multiplier, the `[linkedin.pacing]` knobs spec 9.5 is actually about — the delay between profile views, its spread, the distraction pause, burst size and the break between bursts — the warm-up ramp, LinkedIn auto-send (ADR 0004), every per-day and per-week budget counter against its limit *and* against spec 9.6's hard max, the heat score with when it was last raised (or cleared) and when runs resume, the scheduler's heat skip gate, and whether a schedule is established at all. It reports today's profile-visit budget as the chain that produced it — warm-up ramp, then weekend damping, then the heat cooldown — and states the gaps it cannot see rather than omitting them. `Protection` refuses to exist with a status other than `on` and no warning to go with it, so an "all clear" that hides a disabled protection is structurally impossible; the tests turn each protection off in turn and assert the report warns about that one and only that one. Read-only: it takes no write lock and changes nothing.

The report is careful about what it is entitled to claim. It reads configuration and counters, never callers, so a clean report says *nothing is misconfigured* rather than *every protection is in force* — and it names, in its gap list, the protections that have no enforcing caller in the package yet. That list is derived from a syntax-tree scan of the package rather than hand-maintained, so when P2-06's enrichment job starts calling `budgets.consume` the test fails until the gap is shortened.

`linkedin.timezone` is now the single source of truth for the account's zone: `ensure_local_user` resyncs `User.timezone` from it on every start instead of seeding a new row only. The two are read by different things — budget counters key off the user row, while the active window and the scheduler's deferral read the config — so editing the config after `netkeeper db upgrade` used to leave them permanently disagreeing, which resets a day's budget at an hour the active window is open. Posture keeps its own check of the two as a regression detector.

`netkeeper rehearse` drives the genuine attach path through the genuine pacing plan, built from **your** `[linkedin.pacing]` rather than the library defaults (`netkeeper.services.pacing` is the adapter) — the same scroll deltas, dwell, lognormal waits and bursts a real enrichment run uses — against a profile-shaped replica served on this machine's loopback, and prints every request the tab made: method, status, kind, timing, path, grouped by visit. **It cannot reach LinkedIn:** a linkedin.com host is refused by name, any other off-machine host is refused as not loopback, both before a browser connection exists, and a rehearsal whose page nevertheless reached one raises rather than reporting. The command starts and shuts down the loopback replica itself, so the demo is one command; `--seed` repeats a rehearsal line for line and `--scale` divides the waits, which the log then marks so a scaled rehearsal can never be mistaken for a real one. Nothing launches a browser, nothing opens a database, and requests are observed through a page listener rather than intercepted, so the log records what the browser genuinely sent. Requests that arrive after the last visit — during the tab's own teardown, which is when an unload beacon fires — are logged under their own heading and checked for neutrality like every other request, and when a tab is lost mid-rehearsal the summary drops its absolute claim and says the log is incomplete instead.
