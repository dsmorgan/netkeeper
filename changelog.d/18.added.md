Triage (`netkeeper.crm.triage`, spec 10.2): the queue of untriaged contacts, one at a time, with its evidence in the same response. `GET /api/v1/triage/next` returns a card — the contact, its LinkedIn message history with counts and the newest few, the interaction and job-snapshot timeline, the companies it shares with the rest of the address book, its notes and tags — plus the card after it and the progress counters, so a keyboard run never waits for an evidence round trip. `POST /api/v1/triage/decisions` records `met`, `not_met`, or `skip` and returns the next card with the decision, which makes a run of fifty contacts fifty-one requests and a fixed number of queries per contact whatever history each one carries. `POST /api/v1/triage/undo` restores the previous state exactly, not merely "untriaged": every action writes a `triage_decisions` row (migration `0007`) holding the fields it changed as they were and as it left them, so undo puts back the earlier `met` with its original `triaged_at`, walks back one decision at a time when a contact was decided twice, reaches the decision before once one is spent, and returns the contact to its place in the queue, which is ordered by id and so never depends on a decision. Undo refuses with `409` rather than half-doing the job: when the contact no longer holds what the decision left it holding, so an edit that arrived in between is never overwritten; and when the contact has left the queue since, because neither archiving nor merging touches a recorded field, and restoring a merged-away contact would clear the decision on a row nobody reads while the survivor, which `merge` copied `met` and `triaged_at` onto, quietly kept it. `force` restores anyway and names what it overrode, and a contact named there may be restored without being back in the queue. `PUT /api/v1/triage/contacts/{id}/preferred-name` is the `p` key, written through `set_manual_field` so no later sync, archive, or CSV import overwrites it, and undoable like any decision. `GET /api/v1/triage/suggestions` offers "mark everyone with message history as met" as a preview with a count and nothing else; `POST /api/v1/triage/suggestions/{key}/apply` applies it as one batch that a single undo takes back contact by contact to where each one was, and refuses with `409` when the set has moved on since the count the banner showed. Message bodies and notes are returned exactly as they were stored, HTML and all (#75): the API escapes nothing, so whatever renders `summary` or `notes` must, and a test pins that contract.
