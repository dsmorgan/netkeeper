Triage (`netkeeper.crm.triage`, spec 10.2): the queue of untriaged contacts, one at a time, with its evidence in the same response. `GET /api/v1/triage/next` returns a card — the contact, its LinkedIn message history with counts and the newest few, the interaction and job-snapshot timeline, the companies it shares with the rest of the address book, its notes and tags — plus the card after it and the progress counters, so a keyboard run never waits for an evidence round trip. `POST /api/v1/triage/decisions` records `met`, `not_met`, or `skip` and returns the next card with the decision, which makes a run of fifty contacts fifty-one requests and a fixed number of queries per contact whatever history each one carries. `POST /api/v1/triage/undo` restores the previous state exactly, not merely "untriaged": every action writes a `triage_decisions` row (migration `0007`) holding the fields it changed as they were and as it left them, so undo puts back the earlier `met` with its original `triaged_at`, walks back one decision at a time when a contact was decided twice, reaches the decision before once one is spent, and returns the contact to its place in the queue, which is ordered by id and so never depends on a decision. Undo refuses with `409` when the contact no longer holds what the decision left it holding, rather than overwriting an edit that arrived in between; `force` restores anyway and names what it overrode. `PUT /api/v1/triage/contacts/{id}/preferred-name` is the `p` key, written through `set_manual_field` so no later sync, archive, or CSV import overwrites it, and undoable like any decision. `GET /api/v1/triage/suggestions` offers "mark everyone with message history as met" as a preview with a count and nothing else; `POST /api/v1/triage/suggestions/{key}/apply` applies it as one batch that a single undo takes back contact by contact to where each one was, and refuses with `409` when the set has moved on since the count the banner showed.
