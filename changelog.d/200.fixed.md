A connections sync no longer stops at the first answer whose body Chrome can't return. When the page moves on past a lost answer, netkeeper records the loss and keeps reading.

- A run stops as `answer_lost` only when it loses more than five answers, when the page jumps more than one answer past a lost start, or when the page goes quiet after a loss.
- A run with any loss is incomplete. It ages nobody, is recorded as `aborted` with `stop_reason = answer_lost`, and lists every lost start in its note and in `counts_json.lost`. A loss never counts toward the route-changed breaker.
- The weekly full sync isn't done while its run lost answers. The scheduler offers it again about a day later (with up to three hours of jitter), at most once per week. If that re-offer loses answers too, the full sync waits for its normal weekly time.
- An incremental sync doesn't stop as caught up on the slice that carried a loss, or on the slice right after it.
- A lost answer that is still pending when a wall or a throttle stops the run is recorded too.
- Each lost answer is logged with fixed, non-identifying diagnostics, and each run's observation logs a one-line summary. A lost body's cause now tells "no data" (the request is known, but its body wasn't kept) apart from "no resource".
