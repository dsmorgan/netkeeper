`POST /api/v1/imports/archive` (P1-20): upload the LinkedIn export zip exactly as downloaded and it runs through the same `netkeeper.crm.archive.import_archive` the CLI's `netkeeper import archive` uses, in the request's own transaction, answering per-table counts (connections, messages, invitations) and the tables it did not read. Nothing is decompressed until the upload clears guards on its declared member count (checked before the zip's central directory is even parsed), its total uncompressed size, a member's compression ratio, and a member's path — a zip bomb, a "many tiny files" zip, or a path that would escape the archive is refused with a `422` before any of that, and so is a zip that is not a LinkedIn export, naming the table it expected, and one that is merely damaged (a corrupted download, not only a crafted one). Re-uploading the same export adds nothing. The CLI keeps taking a directory or a zip path and reports the same counts for the same archive as the endpoint does. Every refusal's body carries a stable `code` (`not_a_zip`, `wrong_archive`, `nested_zip`, `encrypted`, `damaged`, `malformed_table`, `too_large`, `too_many_members`, `compression_ratio_too_high`, `unsafe_member_path`) alongside the human-readable message, so the import wizard can act on why an upload was refused without parsing prose that is free to be reworded.
