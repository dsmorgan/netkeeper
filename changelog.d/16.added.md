Tags and auto-tag rules (spec 8.3, 10.3). Migration `0004` adds `tags` (a name unique per user without regard to case, a color, and a kind: `manual`, `auto`, `llm`), `contact_tags` (an assignment with its source, `manual`, `rule`, or `llm`, and the rule it came from), `contact_tag_suppressions` (an automatic tag the user removed, so no rule re-adds it), and `autotag_rules` (a case-insensitive regular expression over the title, headline, or company that feeds one tag, in a user-set order). `netkeeper.crm.tags` creates, renames, and deletes tags, tags and untags contacts (a manual tag takes over an automatic one and clears its suppression; removing an automatic tag writes one), manages rules with the pattern validated at save time (a pattern is refused when an unbounded repeat contains another one, as in `(a+)+`, the shape behind exponential backtracking, or when its counted repeats multiply out past 1000, as in `(?:(?:a{100}){100}){100}`, which `regex` expands at compile time into gigabytes), previews what a pattern would match without writing, and runs the rules: every enabled rule is evaluated in Python over the live contacts in batches, a matched tag is added as a `rule` assignment unless suppressed, a `rule` assignment no enabled rule matches any more is removed, and `manual` and `llm` assignments are never touched. A default set of 13 tags with a title and a headline rule each (c-suite, vp, director, founder, investor, recruiter, engineering, product, design, sales, marketing, consultant, academic) is seeded once per user at first start and recorded in `settings_kv` under `tags.defaults_seeded`, so a default the user deletes stays deleted. The filter language's `tag_any`, `tag_all`, and `tag_none` now compile (names matched without regard to case). API: `GET/POST /api/v1/tags`, `PATCH/DELETE /api/v1/tags/{id}`, `POST /api/v1/contacts/{id}/tags`, `DELETE /api/v1/contacts/{id}/tags/{tag_id}`, `GET/POST /api/v1/autotag-rules`, `PATCH/DELETE /api/v1/autotag-rules/{id}`, and `POST /api/v1/autotag-rules/reorder|run|preview` and `/{id}/run`. CLI: `netkeeper tags list` and `netkeeper tags run-rules`. Every search runs with a 50 ms timeout, so a pattern that slips past the static check cannot hold the SQLite write lock: a search that times out adds no tag and removes none either, so a loaded machine cannot strip tags a quiet one keeps; it is logged with the rule and the contact, and is reported as `timeouts` by the run and preview endpoints and by `netkeeper tags run-rules`. After 20 timeouts a rule is skipped for the rest of the run, which bounds what one slow pattern can cost no matter how large the address book is.
